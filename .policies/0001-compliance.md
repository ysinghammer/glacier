# 0001 — Compliance

1. These policies are a self-contained consolidation of the technology, dependency, architecture, code-style, React, testing, capability-scenario documentation, and development workflow rules. All thirteen policies MUST be read as jointly binding within those scopes. MUST denotes an obligation; MUST NOT denotes a prohibition; MAY denotes only an explicit permission or exception. Applicability qualifiers MUST be respected.
2. Before accepting a project change, contributors MUST check conformance against every accepted, active ADR and manually review requirements not established by tools: architectural boundaries, responsibility/readability, public contracts, dependency approvals, assertion quality, documentation consistency, and affected links. Conflicts MUST be resolved by revising the change or updating the conflicting ADR before acceptance, not by a waiver comment. Suppressions MUST be narrow and justified, not broad file-level escapes.
3. After every code change, contributors MUST run `pnpm run ci` to execute the Turborepo workspace quality gate, resolve Oxlint/Oxfmt violations, and pass applicable type-check/build/test tasks. Editor formatting or direct tool execution MUST NOT replace these gates. Oxfmt defaults MUST own formatting; competing handwritten whitespace, quote, or line-length rules MUST NOT be maintained. Failed/unavailable applicable checks MUST NOT be reported as passing; genuinely inapplicable checks MUST be explained. Documentation-only work MUST verify conformance, consistency, and changed links without claiming product checks ran.
4. GitHub Actions CI MUST invoke the same `ci` task graph through pnpm/Turborepo for builds, lint/format checks, and applicable tests. Required security scans MUST also run through workspace tasks. Workspace/package scaffolding MUST configure applicable compiler, lint/format, test, coverage, catalog/reporting, uncached black-box, and CI gates with real scripts, not empty or skipped checks. A scriptless `ci` aggregation task MAY depend on those executable checks; it MUST NOT require a dummy script or omit applicable gates.
5. Workspace scaffolding MUST install/configure root Husky and activate local hooks. Husky pre-commit MUST run `pnpm exec turbo run ci`, checking the working tree through the workspace task graph rather than only matching staged files. `lint-staged` and `pnpm staged:check` MUST NOT be required; the workspace `ci` gate replaces staged-only checks. Failed checks MUST block commits until corrected; hooks MUST NOT be bypassed or substitute for explicit workspace validation/CI. Hook checks MUST NOT automatically fix, stage, stash, or revert contributor work.
6. Current inline tooling coordinates are `package.json`, `turbo.json`, `tsconfig.base.json`, `.husky/pre-commit`, `.husky/commit-msg`, `.oxfmtignore`, and `pnpm-workspace.yaml`. The quality entry point is `pnpm run ci` (`turbo run ci`); `pnpm exec turbo run ci --force` MUST be used when uncached execution is required. The graph currently includes root `lint:check`/`format:check` and package `lint:types`, `build`, and `test` tasks. Root `pnpm lint:check`/`pnpm format:check` provide focused feedback; `pnpm lint:write`/`pnpm format:write` are explicit mutation commands, not substitutes for the quality gate. Interrupted checks MUST preserve contributor work. Exact declared runtimes MUST be activated rather than bypassing strict engines; frozen-install failures MUST NOT be hidden by removing frozen mode. Automated enforcement or execution not actually available MUST NOT be claimed.
