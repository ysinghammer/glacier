# 0012 — Capability scenario catalog

1. Application/service acceptance criteria MUST be drafted during discovery from intended outcomes, public contracts, and relevant existing behavior, not inferred from finished code. Ambiguous outcomes/permissions/rejections/boundaries MUST be resolved with the user. Briefs MUST propose scenario additions/modifications/removals with stable IDs, acceptance criteria, and rationale; plan approval MUST include user approval of those criteria before implementation. Approved scenarios MUST enter the capability documentation before feature implementation. Planned scenarios lacking tests MUST remain visible unfinished work.
2. `tests/scenarios/README.md` MUST be the global capability index. It MUST list every documented capability, briefly explain what it does and its business value, and link relatively to `tests/scenarios/<capability>/README.md`. It MUST NOT duplicate the capability's scenario definitions or test mappings. Capabilities MUST follow business outcomes, not frontend/backend packages or interfaces.
3. Each `tests/scenarios/<capability>/README.md` MUST explain the capability's purpose, business function/value, and relevant public UI/HTTP contracts, including HTTP method/path where applicable. It MUST act as the complete index of that capability's required scenarios, including unfinished scenarios. Each scenario MUST have a stable globally unique ID, a descriptive title, the business function/value it verifies, requirement/public-contract source references, acceptance criteria, and relative links to the actual Playwright tests proving those criteria. Acceptance criteria and scenario definitions MUST be authored in this Markdown, not a separate typed TypeScript inventory, executable tests, or a required Gherkin/Cucumber format. `tests/acceptance/` MUST NOT exist; validation/support belongs outside the scenario documentation in the paths defined by policy 0011.
4. Each scenario MUST describe concrete test-owned personas/data and express observable acceptance criteria: Given specifies actor, permissions, independently achievable public preconditions; When specifies the business action/public request; Then specifies objectively assertable UI/API outcomes with measurable timing/limit bounds where relevant. Selectors, drivers, fixture implementation, internal calls, and database contents MUST NOT define acceptance criteria. Distinct rejection/authorization rules MUST have separate named scenarios. Every capability's documented public functions/contracts MUST have scenarios covering applicable success, rejection, authorization, and boundaries. Cross-capability journeys MUST be documented once under their verified capability outcome and MAY link to related capability documentation.
5. Scenario IDs MUST be stable and globally unique, not filename/story-dependent, renumbered, or reassigned. Modifications of the same behavioral rule MUST preserve its ID; distinct rules MUST get new IDs. Behavioral changes/removals MUST receive renewed user approval; removals MUST explain why behavior is no longer required, not cite inconvenient/failing tests. Deprecated but supported behavior and unaffected regression scenarios MUST remain required. Behavior-preserving implementation changes need no renewed criterion approval. Git history MUST preserve prior definitions, not in-file revision logs.
6. Capability Markdown MUST own the durable current approved baseline; briefs MUST retain proposals/rationale and references without duplicating that baseline. Archival MUST preserve references without moving active scenarios out. Nonapplication documentation/tooling/library work MUST retain story-local criteria (for example `AC-001`, qualified by story outside it), and applicable validation, without invented business capability/scenario entries.
7. Completed scenario entries MUST link to every test needed to prove their criteria and identify the corresponding test by scenario ID. A link to a spec alone MUST NOT imply all its tests prove that scenario. Planned scenarios MUST be explicitly marked unfinished with intended test paths as plain code, not links claiming implemented evidence. Test-owned persona/data definitions MAY be shared through relative references, without a separate typed acceptance inventory or production imports. Coverage summaries and reverse mappings MUST be derived from the documented scenarios and discovered tests, not maintained as duplicate inventories.
8. Validation MUST reject missing capability documentation/global index entries, malformed or duplicate scenario IDs, undocumented public functions/contracts without required scenarios, broken source/test/persona/data references, scenarios without discovered tests, and discovered tests without documented scenarios. Missing planned tests MUST fail until completed, not disappear. Reports MUST show capability → scenario → test mappings and execution outcomes, with scenario IDs/reasons, retained `validation.json`, and nonzero failure; exceptional filesystem failure MUST propagate, not become an empty inventory. Authored validation MUST live in `tests/verification/`, with generated reports under the invocation-isolated artifacts defined by policy 0011.
9. Static foundation discovery MUST require one exact top-level `// @scenario SC-001` line per scenario ID in capability-owned specs, using the actual documented ID. Missing/duplicate/unknown metadata and symbolic links in the scenario tree MUST fail discovery. Validation MUST match documented test links to the specs declaring those IDs. Static discovery MUST NOT execute specs or imply assertion/execution success. Static-only reports MUST truthfully use `execution.status: "not-run"` and `execution.results: null` until actual results exist. The first application implementation MUST add per-test execution reporting and skipped/focused/retry-only failure controls.
10. Review MUST establish that assertions prove each linked scenario's documented business function/value and acceptance criteria. Mapping completeness, assertion quality, actual execution, and instrumentation code coverage MUST remain distinct; Playwright feature/contract coverage MUST NOT be described as code coverage. Before acceptance, scenario documentation validation and the complete actual uncached Playwright suite MUST pass locally/CI through pnpm/Turborepo alongside applicable library gates. Filtered/focused/skipped tests and retry-only passes MUST NOT satisfy acceptance; diagnostic retries MUST NOT conceal flaky failure.
11. Every story plan MUST retain `E2E tests`. Application/service changes MUST describe capabilities, scenario IDs, intended Playwright paths, and approved brief criterion proposals. Before completion, relative links MUST point to actual implemented tests and capability scenario documentation, retaining scenario IDs identifying tests; planned paths MUST NOT masquerade as completed links. Plans without application/service changes MUST justify E2E inapplicability and describe applicable library/other checks in `Validation`. Criterion verification-method mapping MUST NOT duplicate derived scenario coverage summaries.
