# 0006 — TypeScript and implementation

1. Standalone behavior MUST use classes, including use cases/factories; utilities MUST use static methods on purpose-specific classes, not global utility containers. Stateless behavior MUST NOT require artificial state. Plain records, interfaces, and aliases MAY describe data; behaviorless classes MUST NOT be manufactured merely to hold it.
2. Functions MUST be limited to framework/platform-required entry points and callbacks, including React components/hooks/React-required callbacks. Callbacks MUST remain focused and delegate substantial behavior to named methods; this exception MUST NOT convert unrelated standalone behavior into functions.
3. Code MUST prioritize readable explicit control flow over clever expressions, compressed statements, nested ternaries, and abstractions merely reducing line count. Methods/files MUST have cohesive responsibilities; guard clauses MUST be used where clearer. Complexity MUST follow the requirements below; arbitrary line-count limits are not prescribed. Bindings MUST default to `const`, use `let` only for reassignment, and MUST NOT use `var`. Nonmutating contracts MUST use readonly members/collections. Every class property and method, including static members and accessors, MUST declare an explicit `public`, `private`, or `protected` access modifier; implicit public access MUST NOT be used. Native `#` private properties and methods MUST NEVER be used.
4. Speculative abstractions, dead code, unexplained magic values, and accidental import-time effects MUST NOT be introduced. Named constants MUST explain meaningful fixed values; reuse MUST respect semantic ownership.
5. Compiler configuration MUST enable `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, `noUnusedLocals`, `noUnusedParameters`, and `noFallthroughCasesInSwitch`. Current `tsconfig.base.json` also enables `verbatimModuleSyntax` and `forceConsistentCasingInFileNames`, with ES2023/NodeNext module resolution. Module syntax/extensions MUST follow actual build/runtime configuration, not an invented universal extension convention; React runtime imports MUST match JSX configuration.
6. Clear local types MUST be inferred. Public methods and permitted exported functions MUST declare return types. Untrusted values MUST enter as `unknown` and be narrowed/validated. Routine `any`, unchecked assertions, non-null assertions, and `@ts-ignore` MUST NOT be used. Unavoidable interop exceptions MUST be narrow, justified, and preserve surrounding contracts. Finite scalar choices MUST use string-literal unions, not enums.
7. Type-only imports MUST use `import type`. Source files MUST have at most one primary named export (entries MAY have none), with only supporting interfaces needed to describe/consume it as additional exports. Supporting aliases and unrelated interfaces MUST have their own files; private helpers/types MUST remain unexported. Default exports MUST be limited to externally mandated conventions.
8. `.stories.tsx` MAY export default Storybook metadata and multiple named stories, but no unrelated exports or production barrels. A library's curated package-root `index.ts` is the sole barrel/multiple-public-export exception. Reflection's minimal package-root `register.ts` has zero public symbols and only delegates explicit compiler protocol activation; it is not another barrel. All other barrels and convenience re-exports, including nested/application `index.ts`, MUST NOT exist. Public application capability APIs MUST be explicitly identified single-export files.
9. Intra-package imports MUST be relative, including public cross-capability files. Inter-package imports MUST use the supplying package's public root, never relative traversal, deep imports, or public subpaths, with only the side-effect import `import "@glacier/reflection/register"` permitted for explicit compiler registration. All ordinary values/types remain public-root-only. TypeScript path aliases/equivalent internal import aliases MUST NOT be used; ordinary package names and type declarations are not aliases.
10. Every class, class constructor, class method, class property, accessor, interface, interface property, interface method, named type alias, and permitted standalone function MUST have comprehensive JSDoc immediately preceding its declaration. This requirement includes public, protected, private, static, abstract, optional, readonly, exported, and unexported declarations, including permitted standalone functions assigned to variables. Documentation MUST describe functionality and all applicable inputs, properties, return values, failures, mutation, and lifecycle obligations using the JSDoc requirements below; merely repeating names or TypeScript signatures MUST NOT satisfy it. Documenting a class or interface MUST NOT replace documentation on each member. Inline comments MUST explain non-obvious reasons/constraints, not narrate code. Documentation MUST NOT authorize standalone functions otherwise prohibited by this policy.

## Low-complexity control flow

11. Methods and permitted functions/callbacks MUST stay within the cyclomatic and cognitive complexity limits enforced by `complexity/complexity` in root `.oxlintrc.json`. The current configuration uses plugin defaults: maximum cyclomatic complexity 20 and cognitive complexity 15. These are ceilings, not design targets. Readability review MUST also cover code the plugin skips or treats specially, including short methods and React rendering; a passing score MUST NOT justify tangled responsibilities or deep nesting. Contributors MUST NOT raise limits, disable the rule, or exploit its analysis exclusions merely to make a change pass.
12. Contributors MUST reduce nested control flow with clear guard clauses, early returns/continues, and separation of validation, dispatch, transformation, and coordination where those are distinct responsibilities. Substantial branches, nested loops, and compound predicates MUST be extracted into descriptively named, cohesive methods when that makes their intent clearer. Local implementation details MUST remain private methods on the owning class, using static methods when no instance state is needed; permitted callbacks MUST delegate substantial behavior rather than hide it in nested closures. Extraction MUST preserve capability/layer ownership and MUST NOT introduce generic helper containers, artificial classes, or fragmented one-line delegation merely to distribute a score. Finite discriminated choices MAY use exhaustive switches; lookup tables MAY replace branches only when they clearly represent a data mapping, not hide validation or side effects.
13. Extracted methods MUST make required inputs, results, and mutation obligations explicit, using narrowed types and typed outcomes where applicable. They MUST NOT introduce shared mutable state, mode flags combining unrelated operations, unchecked assertions, or success-shaped fallback values to simplify branching. Complexity refactors MUST preserve public contracts, validation/failure distinctions, evaluation order, and observable side effects, with applicable public success, failure, and boundary assertions retained under the testing policies. Plugin extraction suggestions MUST be reviewed against these obligations before adoption; unrelated behavior changes MUST remain separate.

## Comprehensive JSDoc

14. Every required JSDoc block MUST start with a meaningful description of what the declaration does, its responsibility, and how callers or implementers use it. Documentation MUST be as complete as the declaration's actual contract requires, including applicable invariants, preconditions, validation, side effects, state changes, ownership, resource lifecycle, and boundary behavior. Class and interface documentation MUST explain the overall contract and the role of their properties and operations; named type aliases MUST explain the represented values and constraints. Private implementation details MUST be documented at their owning declarations rather than exposed as public guarantees. Redundant filler, unsupported guarantees, and irrelevant tags MUST NOT be added merely to increase documentation volume.
15. Constructors, methods, interface methods, callable properties, accessors accepting input, and permitted standalone functions MUST document every parameter with one named `@param` tag explaining its meaning, operation-specific constraints, and applicable optional/default behavior. Object and destructured object parameters MUST be documented as a whole and refer to their documented interface where applicable; their properties MUST NOT have nested `@param` entries or be duplicated through `@property` tags in the operation's JSDoc. Property descriptions MUST belong to the owning interface or data contract, not be repeated at each call site. Generic declarations MUST use `@template` to explain each type parameter's role and constraints. TypeScript MUST remain the source of truth for types; JSDoc MUST NOT introduce conflicting or redundant type expressions where TypeScript already supplies them.
16. Every class property and interface property MUST have its own JSDoc describing what the value represents, how it is used, and applicable units, valid values, defaults, optionality, readonly/mutability, ownership, and initialization or lifecycle constraints. Callable properties MUST additionally document their callable contract with `@param`, `@returns`, and applicable `@throws` tags. Aggregate class, interface, or type documentation MUST use `@property` tags when describing fields not represented by individually documented member declarations; aggregate tags MUST NOT substitute for required member documentation. Applicable default values MUST use `@default`; an absent or computed default MUST NOT be described as a fixed value.
17. Methods, interface methods, getters, callable properties, and permitted standalone functions MUST use `@returns` to explain the returned value, its meaning, and applicable success/rejection variants, optional or empty results, identity, ownership, and mutation guarantees. Asynchronous operations MUST describe what the returned promise resolves to and any completion/lifecycle guarantees, not merely say that they return a promise. Operations returning `void` MUST explicitly state that they return no value and describe their observable effect; constructors and setters MUST describe their construction or mutation effects without inventing a return value or adding an inapplicable `@returns` tag.
18. Each constructor, method, accessor, callable property, or permitted standalone function MUST document only exceptions thrown directly by its own body with `@throws {ErrorType}` and the precise condition causing each throw. Direct throws include explicit wrapping or rethrowing in that body, but MUST NOT include errors merely propagated from called methods, functions, constructors, or nested callbacks. Such errors MUST remain documented at the declaration that directly throws them, not duplicated in callers' JSDoc. An asynchronous body's direct throws MUST be documented as promise rejections rather than synchronous throws. Interface methods and callable signatures MUST document only direct-throw obligations explicitly required of their implementations. Operations with no direct throws MUST omit `@throws`; omission MUST NOT be described as a guarantee that called operations cannot fail. Fictitious exception types or failure guarantees MUST NOT be added. Expected typed validation/business rejections MUST be documented in `@returns`, not misrepresented as thrown exceptions, preserving policy 0007's transport-boundary exception. Applicable examples, `@remarks`, `@see`, and `@deprecated` guidance MUST be included when needed to explain non-obvious use, constraints, related contracts, or supported migration. Contributors MUST review JSDoc completeness and accuracy alongside each changed declaration and keep it synchronized with behavior; passing lint or type checks MUST NOT substitute for this review.
19. The main description of each JSDoc block MUST NOT exceed 200 characters; each complete `@`-prefixed tag entry MUST NOT exceed 100 characters, including its tag name, parameter/property name, type expression, and description. Limits apply to the entire description or tag entry, not individual wrapped lines. Counting MUST use Unicode code points after removing comment delimiters and leading comment-line `*` formatting, trimming surrounding whitespace, and joining whitespace runs with one space. Required contract coverage MUST be retained through concise wording and applicable tags or references to documented contracts. Separate `@throws` entries MAY describe distinct failure conditions of the same error type; wrapping text, splitting one description across redundant tags, or adding filler tags MUST NOT evade these limits.
