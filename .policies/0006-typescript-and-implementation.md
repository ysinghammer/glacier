# 0006 — TypeScript and implementation

1. Standalone behavior MUST use classes, including use cases/factories; utilities MUST use static methods on purpose-specific classes, not global utility containers. Stateless behavior MUST NOT require artificial state. Plain records, interfaces, and aliases MAY describe data; behaviorless classes MUST NOT be manufactured merely to hold it.
2. Functions MUST be limited to framework/platform-required entry points and callbacks, including React components/hooks/React-required callbacks. Callbacks MUST remain focused and delegate substantial behavior to named methods; this exception MUST NOT convert unrelated standalone behavior into functions.
3. Code MUST prioritize readable explicit control flow over clever expressions, compressed statements, nested ternaries, and abstractions merely reducing line count. Methods/files MUST have cohesive responsibilities; guard clauses MUST be used where clearer. Complexity MUST follow the requirements below; arbitrary line-count limits are not prescribed. Bindings MUST default to `const`, use `let` only for reassignment, and MUST NOT use `var`. Nonmutating contracts MUST use readonly members/collections. Every class property and method, including static members and accessors, MUST declare an explicit `public`, `private`, or `protected` access modifier; implicit public access MUST NOT be used. Native `#` private properties and methods MUST NEVER be used.
4. Speculative abstractions, dead code, unexplained magic values, and accidental import-time effects MUST NOT be introduced. Named constants MUST explain meaningful fixed values; reuse MUST respect semantic ownership.
5. Compiler configuration MUST enable `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, `noUnusedLocals`, `noUnusedParameters`, and `noFallthroughCasesInSwitch`. Current `tsconfig.base.json` also enables `verbatimModuleSyntax` and `forceConsistentCasingInFileNames`, with ES2023/NodeNext module resolution. Module syntax/extensions MUST follow actual build/runtime configuration, not an invented universal extension convention; React runtime imports MUST match JSX configuration.
6. Clear local types MUST be inferred. Public methods and permitted exported functions MUST declare return types. Untrusted values MUST enter as `unknown` and be narrowed/validated. Routine `any`, unchecked assertions, non-null assertions, and `@ts-ignore` MUST NOT be used. Unavoidable interop exceptions MUST be narrow, justified, and preserve surrounding contracts. Finite scalar choices MUST use string-literal unions, not enums.
7. Type-only imports MUST use `import type`. Source files MUST have at most one primary named export (entries MAY have none), with only supporting interfaces needed to describe/consume it as additional exports. Supporting aliases and unrelated interfaces MUST have their own files; private helpers/types MUST remain unexported. Default exports MUST be limited to externally mandated conventions.
8. `.stories.tsx` MAY export default Storybook metadata and multiple named stories, but no unrelated exports or production barrels. A library's curated package-root `index.ts` is the sole barrel/multiple-public-export exception. Reflection's minimal package-root `register.ts` has zero public symbols and only delegates explicit compiler protocol activation; it is not another barrel. All other barrels and convenience re-exports, including nested/application `index.ts`, MUST NOT exist. Public application capability APIs MUST be explicitly identified single-export files.
9. Intra-package imports MUST be relative, including public cross-capability files. Inter-package imports MUST use the supplying package's public root, never relative traversal, deep imports, or public subpaths, with only the side-effect import `import "@glacier/reflection/register"` permitted for explicit compiler registration. All ordinary values/types remain public-root-only. TypeScript path aliases/equivalent internal import aliases MUST NOT be used; ordinary package names and type declarations are not aliases.
10. Classes, methods, interfaces, named type aliases, and permitted standalone functions MUST have JSDoc describing purpose and applicable inputs, outcomes, failures, mutation, and lifecycle obligations, not merely repeating names. Inline comments MUST explain non-obvious reasons/constraints, not narrate code.

## Low-complexity control flow

11. Methods and permitted functions/callbacks MUST stay within the cyclomatic and cognitive complexity limits enforced by `complexity/complexity` in root `.oxlintrc.json`. The current configuration uses plugin defaults: maximum cyclomatic complexity 20 and cognitive complexity 15. These are ceilings, not design targets. Readability review MUST also cover code the plugin skips or treats specially, including short methods and React rendering; a passing score MUST NOT justify tangled responsibilities or deep nesting. Contributors MUST NOT raise limits, disable the rule, or exploit its analysis exclusions merely to make a change pass.
12. Contributors MUST reduce nested control flow with clear guard clauses, early returns/continues, and separation of validation, dispatch, transformation, and coordination where those are distinct responsibilities. Substantial branches, nested loops, and compound predicates MUST be extracted into descriptively named, cohesive methods when that makes their intent clearer. Local implementation details MUST remain private methods on the owning class, using static methods when no instance state is needed; permitted callbacks MUST delegate substantial behavior rather than hide it in nested closures. Extraction MUST preserve capability/layer ownership and MUST NOT introduce generic helper containers, artificial classes, or fragmented one-line delegation merely to distribute a score. Finite discriminated choices MAY use exhaustive switches; lookup tables MAY replace branches only when they clearly represent a data mapping, not hide validation or side effects.
13. Extracted methods MUST make required inputs, results, and mutation obligations explicit, using narrowed types and typed outcomes where applicable. They MUST NOT introduce shared mutable state, mode flags combining unrelated operations, unchecked assertions, or success-shaped fallback values to simplify branching. Complexity refactors MUST preserve public contracts, validation/failure distinctions, evaluation order, and observable side effects, with applicable public success, failure, and boundary assertions retained under the testing policies. Plugin extraction suggestions MUST be reviewed against these obligations before adoption; unrelated behavior changes MUST remain separate.
