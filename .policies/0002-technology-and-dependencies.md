# 0002 — Technology and dependencies

1. Project-authored application, service, library, and test code MUST use TypeScript. Server-side TypeScript and workspace tooling MUST use active Node.js LTS; package management MUST use pnpm and local/CI workspace tasks MUST use Turborepo. The shared quality entry point MUST be `pnpm run ci` (`turbo run ci`), with root Husky pre-commit invoking the same graph through `pnpm exec turbo run ci`, not `lint-staged`. Linting MUST use Oxlint; formatting MUST use Oxfmt. Current exact configuration pins are Node `24.21.0` in `.node-version`, `.nvmrc`, and manifests, and pnpm `11.9.0` in `package.json`; these pins implement, not replace, the active-LTS standard. `pnpm-workspace.yaml` discovers `packages/apps/*`, `packages/services/*`, and `packages/libraries/*` with strict engines, without requiring placeholder products.
2. Deployable backend services MUST be Docker images. Local development MAY run outside Docker except where tests require containers. Frontend applications MUST use React built with Vite. Services needing relational persistence MUST use PostgreSQL, Drizzle ORM access, and Drizzle Kit migrations; services needing shared caching MUST use Redis. These needs MUST NOT be manufactured for services without them.
3. Snyk MUST perform dependency and applicable container-image security scans; Renovate MUST propose automated dependency updates. Both MUST be GitHub integrations, not direct npm dependencies. Node, pnpm, Docker, and GitHub Actions are platform/workspace choices, not prescribed npm dependencies.
4. Every NEW direct runtime/development dependency MUST receive explicit approval before addition, including listed packages; approval MUST remain within its listed scope. Transitively supplied dependencies of approved direct dependencies require no separate approval. Unlisted framework, HTTP/validation, hosting, styling/routing, and other product-dependent choices remain unspecified, not prohibited; this policy does not newly prescribe or restrict those choices. Any new direct runtime/development dependency still MUST receive explicit approval before addition. Current versions normally belong in manifests, not a blanket permission to upgrade.

5. Root commitlint configuration MUST use Conventional Commits header rules with exactly one scope, `workspace` or a workspace package directory name minus `glacier-`, derived from `pnpm-workspace.yaml`. Root Husky `commit-msg` MUST run `pnpm exec commitlint --edit "$1"`; CI MUST check each PR commit independently against the root configuration. This bounded tooling contract does not migrate or authorize commit workflow.
6. `@glacier/reflection` MUST remain technology-neutral, native ESM, ES2023, with exactly two generated public entries: `"."` using `dist/index.js`/`dist/index.d.ts` and `"./register"` using `dist/register.js`/`dist/register.d.ts`. It MUST have no runtime dependencies, CommonJS entry, wildcard, deep imports or other public subpaths. Its package-local development pins are `vitest` and `@vitest/coverage-v8` exactly `5.0.3`, and Vite exactly `8.3.2`; shared TypeScript/Node tooling remains workspace-owned. Vite approval is solely for independent non-React distribution verification, including explicit-registration retention, inactive side-effect-only and used ordinary roots, and shared root/registration metadata, not production compilation or runtime Vite. It MUST NOT imply approval of DI, reflect-metadata, schema validation, React, another bundler, or React-only testing packages. Runtime verification is Node-only, bounded to Node 24 LTS (workspace `24.21.0`), not browser/historical compatibility or npm publication. Reflection verification MUST NOT require a browser project, direct Playwright dependency or Chromium installation; other libraries' applicable browser and React testing standards remain unchanged.
7. Reflection runtime root imports, including side-effect-only imports, MUST NOT inspect or mutate global Reflect or activate compiler recording; type-only imports also remain inactive. Only `import "@glacier/reflection/register"` intentionally installs `Reflect.metadata`, with zero public symbols and exactly `sideEffects: ["./dist/register.js"]`. Consumers migrating from automatic root activation MUST add this import in static composition before importing modules whose legacy decorated declarations execute, and enable `experimentalDecorators`/`emitDecoratorMetadata`. Modern standard decorators and retroactive recovery of missed emissions are unsupported. Manual metadata operations/decorators remain usable without registration when normal Reflect intrinsics are available; ambient compiler typing does not guarantee handler availability. Activation MUST NOT start resources, background work, registries, or consumer instances or install the general reflect-metadata API.
8. Ordinary root imports MUST succeed under foreign metadata handlers and duplicate physical package copies without replacing descriptors or invoking foreign accessors; explicit registration MUST reject these conflicts safely. Repeated imports of the same resolved registration module use module caching and preserve the handler and records, unlike a separately evaluated physical copy. Recovery MUST correct imports/dependencies and restart the process/browser realm, not delete handlers or use unsupported reset/uninstall/toggle operations. Compiler representations are bounded functions/classes or `undefined`, not reconstructed interfaces, generic arguments, parameter names, declaration kinds, signature equivalence, or usable dependency constructors. Explicit typed-symbol annotations MAY supply erased interface identity; retrieval is not DI resolution or consumer construction. These contracts MUST NOT broaden other libraries' scopes.
